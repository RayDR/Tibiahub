## 6–7. Raw contract and adapter

The provider catalog is bounded to 50 members per page and continuation tokens are persisted by the durable job system. Main-namespace entries are emitted as independent detail jobs. Namespace pages and the aggregate `Hunting Places` page are rejected observably. A detail becomes canonical only when its immutable raw wikitext contains the provider's explicit `Infobox Hunt`; category membership alone is stored as a raw document and normalized as `noop` with `unstructured_hunt_zone_page`.

Each detail retains provider `tibiawiki`, numeric page ID, `hunt_zone:<pageid>` document identity, raw JSON, MediaWiki version, retrieval time, job, attempt, and correlation IDs. Modern and legacy Mapper syntax is removed from displayed location prose but remains in immutable raw JSON. No coordinates are parsed from it.

Catalog acquisition result:

- 10 catalog pages, 462 members;
- 4 invalid/non-entity members: `Hunting Places` and three `User:` pages;
- 458 unique detail documents fetched successfully;
- 445 documents with explicit structured zone evidence;
- 13 raw-only aggregate/subarea documents, including `Forsaken Mine`, `Poacher Caves`, and the named Demon Forge subsection pages;
- zero terminal failed external IDs after replay-safe retries.

## 8–10. Canonical identity, mappings, and aliases

Resolution order is: existing `(provider, entity type, external ID)` mapping; exact canonical name or exact verified alias when uniquely available; provider-defined creation; explicit conflict. Matching is type-constrained and exact-normalized only. Similar names never merge. Two authoritative records may retain the same display name with distinct provider IDs, UUIDs, bridge rows, and collision-safe slugs; the three provider-defined `Poacher Caves` records exercise this rule in development.

The bridge never promotes or overwrites a same-name legacy row. Provider bridge identity is `(source_provider, external_id)` and canonical identity is the Knowledge UUID. The schema therefore permits provider/legacy name coexistence and multiple real provider mappings to one canonical entity where another normalizer proves that identity.

Only the explicit difference between MediaWiki page title and `Infobox Hunt.name` becomes an alternative alias. Casing/spacing normalization uses the existing exact contract. Replay does not duplicate aliases; collisions are not chosen arbitrarily. A provider rename keeps UUID and mapping, retains the prior name alias, and moves the canonical name only when collision-free. Removal does not hard-delete or silently supersede a canonical entity; it remains for lifecycle review.

## 11–16. Relationships and spatial behavior

Creature names resolve in batches against exact canonical names/verified aliases and the permitted Creature/Boss types. Missing names create unresolved graph evidence, never a Creature. Bosses are not classified by name; 219 resolved memberships target Creature rows already classified as bosses. The graph's inverse vocabulary supplies `appears_in` views without duplicate inverse writes.

Only explicit access-language evidence creates `requires_hunt_quest`. Generic mentions do not become access, and this provider record does not assert `unlocks_access` or generic related edges. Quest resolution is exact and unresolved names remain reviewable.

`city` and free-form `location` remain separate. A structured city resolves exactly to canonical `town` or `location`; unresolved city names remain review records. Full location prose stays on `HuntZone.region` and creates an edge only if the complete value exactly matches an `area`/`location`. City or prose never becomes geometry.

World Map marker reconciliation reuses the Phase 3A/3D contract. Exact canonical names/explicit aliases may resolve a TibiaMaps marker; cross-type or multi-zone collisions remain ambiguous. No second coordinate precedence path exists. There are no provider bounds or direct provider points in this source.

## 17–19. Media and metadata

Only an explicit `image` field becomes a provider media reference; the prior synthetic `<zone-name>.gif` behavior is removed. Uncached provider references are `reference_only` in the public projection, so the API does not hotlink them. The existing image phase now links successful Hunting Zone caches through `map_asset_id`, uses stable `zone:<provider>:<external-id>` keys, and skips all 973 legacy TibiaMaps floor-image placeholders.

TibiaWiki supplies qualitative `exp`/`loot` text and star ratings, but no normalized, stable per-hour unit. These values are retained as qualitative provider metadata; `avg_exp_hour` and `avg_profit_hour` stay null. Explicit vocation-specific level/skill/defense values remain separated in raw canonical metadata. `min_level` is populated only from explicit provider recommendations. No level comes from Creature difficulty and no difficulty is inferred.

## 20–28. API, coexistence, production, and review

Phase 3B list/detail projections remain the public contract. Canonical rows naturally expose UUID, provenance, completeness, relationships, spatial state, and reference-only/local media. Name/slug detail and map context prefer the canonical provider bridge when a retained legacy row has the same name; numeric legacy IDs remain exact. Public text search remains discovery-oriented while normalization remains exact-only.

The Phase 3D map layer is unchanged in concept: exact marker-resolved zones become point results and knowledge-only zones remain searchable without fabricated markers. Legacy HuntZone and SpawnLocation data are not deleted or attached by name.

The normal production entry point is the durable `tibiawiki/hunt_zone_catalog` Knowledge job, included in TibiaWiki bootstrap and Knowledge Full Sync. Provider registry definitions are refreshed during bootstrap/planning so the durable `hunt_zone` capability cannot remain stale. Manual catalog enqueue requires explicit catalog confirmation. Jobs are bounded, continued, retried, observable, and rate-limited at 12 TibiaWiki requests per 60 seconds. The old direct category-title sync and direct `_upsert_hunt_zone` are explicitly disabled.

Historical backfill used that same catalog/detail adapter and normalizer. Stored-document repair used `hunt_zone_renormalize`, not SQL or alternate semantics. Current unresolved Creature, Quest, and city edges appear in the existing Knowledge Relationship Review with source zone, provider, document, target type/name, state, and provenance. No Hunting Zone-specific review surface was introduced.

## 34–37. Replay, failures, lifecycle, and performance

The final two complete stored-document replays each processed 458 records with 454 successes and 4 partial successes. Both produced exactly 445 entity UUIDs, 445 mappings, 457 aliases, 4,172 current relationships, mapping hash `fc8624c926485e6069c08de66aa954ab8b7df4257e1199dfa2657abdc72af6a0`, and relationship hash `cd51ae7ae996ba370fbdbb1a8dd6d2eb29eae57612dae166808faab28ef08fe3`. No raw document, current relationship, unresolved reference, alias, mapping, media link, or UUID was duplicated.

The initial live run retains eight failed job records caused by the pre-migration unique-name/column-width constraints. Five had already succeeded through retry and the final three were explicitly re-enqueued; all 458 external IDs now have a successful/partial outcome. Failures remain auditable. A malformed detail cannot invalidate sibling detail jobs, and invalid catalog members yield partial catalog success plus valid child jobs.

Provider rename is mapping-led and UUID-stable. Provider removal intentionally does not hard-delete; automatic catalog-wide staleness retirement remains a later lifecycle decision.

The live acquisition ran from `2026-09-02T18:04:57Z` to `19:34:05Z` (5,348.28 seconds including schema diagnosis, validation pauses, and retries) under the 12/minute provider limit. The worst representative zone contained 47 source Creature names. After eager-loading exact candidates and aliases, replay took about 351 ms and 263 SQL statements in this development database; canonical/alias target lookups fell from 58 to 14 and no longer scale one lookup per Creature. The remaining linear work is provenance-aware document/current-relationship reconciliation, appropriate at the 445-zone scale; no distributed processing is warranted.

## 42–44. Remaining gaps and next phases

Remaining Phase 3E data gaps are honest: 13 category records are not independently structured zones; 10 Creature names, 6 access quests, and 390 city relationships remain unresolved; 4 zones have ambiguous exact marker identity; 387 have no marker; there are no zone bounds; numeric EXP/profit and difficulty have no source; provider images still require the normal cache phase; and provider-removal lifecycle review is not automated.

Phase 3F Hunt Planner requirements:

1. consume canonical UUID-backed list/detail projections, never `Creature.locations` identity;
2. distinguish unknown from zero for level, vocation, EXP and profit;
3. decide and document how qualitative ratings participate in ranking before using them;
4. expose completeness/provenance and allow knowledge-only zones without pretending they are mapped;
5. retain explicit compatibility fallback while measuring the remaining 2,654 legacy-only SpawnLocation links;
6. use resolved access requirements and never reinterpret generic Quest evidence.

Phase 3G NPC Directory requirements:

1. keep NPC UUID/provider mappings as identity and reuse canonical Location/spatial contracts;
2. do not infer NPC-to-zone relations from shared prose or proximity;
3. add zone context only when a provider supplies an explicit exact relationship;
4. preserve local-first media, provenance, unknown fields, pagination, and canonical navigation;
5. surface unresolved/ambiguous NPC/Location evidence through the existing Knowledge Review rather than a new review system.
