# TibiaHub V1.3 — Phase 3F Guild Hunt Planner canonical zone audit

Date: 2026-09-02

## Outcome

Phase 3F adds an optional, durable `GuildHunt.hunting_zone_id` reference to a canonical `KnowledgeEntity` UUID. Existing scheduled hunts remain valid with only their original manual fields. No historical row was rewritten, no free-text value was matched, and no Knowledge data is copied into Guild Hunt persistence.

Development data after the migration contains 0 scheduled Guild Hunts (0 canonical, 0 custom). The picker query exposes the 445 active/public canonical Hunting Zone bridges and excludes all 973 legacy-only rows.

## Existing Hunt model audit

- `location`: required operator-entered place text. It remains usable for a custom hunt and remains an independent compatibility/note field for a canonical hunt.
- `target`: required operator-entered purpose/title-like text shown as the card heading. There is no separate Hunt title/name field.
- `description`: optional guild planning notes; canonical selection never rewrites it.
- `scheduled_at` and `timezone_name`: the scheduled instant and the IANA timezone context captured by the form.
- `status`: `scheduled`, `in_progress`, `finished`, or `cancelled`.
- participant fields: one row per user and hunt, with character/vocation snapshot, joined/left timestamps, and `registered`, `attended`, `absent`, or `left` attendance.
- `server_name`, recommended level/vocations, capacity, required vocation slots, Discord channel, and voice channel remain planning metadata.
- authorization remains `hunts.manage` for create/edit/lifecycle/attendance and verified guild membership for viewing/joining.

## Persistence and migration

- Nullable UUID column: `guild_hunts.hunting_zone_id`.
- Foreign key: `knowledge_entities.uuid`, `ON DELETE RESTRICT`, so historical references cannot be cascade-deleted.
- Indexed by `ix_guild_hunts_hunting_zone_id`.
- No zone name, provider page ID, HuntZone legacy ID, relationship graph, media, Creature, Quest, Location, or geometry snapshot is persisted.
- Migration `guild_hunt_zone_20260902` has `hunt_zone_region_20260902` as its parent. Upgrade and downgrade both completed against PostgreSQL; upgrade was then reapplied and one head remains.
- There is intentionally no backfill statement.

## Canonical reference contract

New create/edit input is `hunting_zone_id: UUID | null`. The service accepts it only when:

1. the Knowledge entity exists;
2. `entity_type == "hunt_zone"`;
3. status is `active` and visibility is `public` for a new/changed selection; and
4. an authoritative `HuntZone.knowledge_entity_id` bridge exists.

Arbitrary UUIDs, cross-type Knowledge entities, retired/private entities, and canonical entities without a domain bridge are rejected. Legacy `HuntZone.id` is never accepted as canonical identity.

Historical linked entities remain readable after retirement. The response marks the summary `is_current: false`; the UI asks the editor to choose another canonical zone or switch to custom. Hard deletion is restricted by the foreign key. Provider mapping changes do not affect the stored canonical UUID.

## Create/edit and custom compatibility

- Create supports custom mode with `hunting_zone_id = null` and canonical mode with a separate UUID.
- Edit supports custom→custom, custom→canonical, canonical→canonical, and canonical→custom.
- Clearing the canonical zone explicitly stores `NULL`.
- Location, target, description, party, participants, attendance, scheduling, and lifecycle are not rewritten during zone changes.
- Failed mutations keep the selected zone and form state.
- All historical rows serialize with a null reference and null summary.

## Picker and preview

- The existing `/hunt-zones/` list API gained `canonical_only=true`; it joins active/public `KnowledgeEntity` Hunting Zones.
- The Planner requests at most 8 results, uses partial text search only for discovery, debounces by 250 ms, and aborts stale requests.
- Results are filtered again client-side for `identity_state == canonical` plus a UUID.
- The picker is a keyboard-operable combobox/listbox with arrow, Enter, Escape, selected-state, labels, live status, and a clear action.
- Custom mode stays one click away and does not infer an entity from manual text.
- After selection, the lightweight row is immediately usable and the existing detail API enriches the preview without invalidating the selection if detail loading fails.

The selected preview conditionally renders canonical name, region/location, real level/difficulty/vocation metadata, up to four deterministic Creature rows, authoritative Boss badges, access requirements, Quest links, safe media, map availability, and zone detail navigation. Unknown values are omitted or labeled unknown; EXP/profit are not rendered as zero.

## Creature, Boss, Quest, map, and media behavior

- Creature preview consumes the canonical Phase 3B/3E projection and remains bounded to four entries. `+N`/detail navigation covers larger sets.
- Boss presentation uses only the projected authoritative `is_boss` value.
- `access_required === true` is the only state rendered as required access. Resolved Quests navigate by slug/ID to TibiaHub Quest detail. Generic related Quests are not promoted to requirements. Null access remains explicitly unknown.
- Mapped zones build navigation with `buildMapEntityUrl`, canonical UUID, entity type, slug/name, and trusted floor. The Planner does not reconstruct coordinates.
- Knowledge-only/unresolved geometry remains selectable and displays “exact map position not yet resolved.” No fallback marker is fabricated.
- Only `representative_media.status == "available"` can become an image URL. `reference_only` media is suppressed; the preview uses the canonical map or a semantic Tibia icon instead.

## API projection and query behavior

Guild Hunt responses expose `hunting_zone_id` and an optional bounded `hunting_zone_summary`. The summary contains display identity, location/level metadata, four Creature previews, counts, one resolved required Quest preview, spatial status/floor, safe media URL, and current-state flag. It does not contain a complete relationship graph.

List/calendar projection collects all distinct UUIDs and calls the existing Hunting Zone projector once for the whole set. A regression test verifies the SQL statement count is identical for one and two distinct linked zones and stays below 20 statements. Guild manage/member capability checks are also computed once for the single-guild list instead of once per Hunt. Full zone detail is loaded only for create/edit selection context.

## Audit behavior

Creation audit metadata stores only canonical UUID and useful label when selected. Edit audit metadata records `from` and `to` UUID/label when the zone changes. It does not copy zone snapshots, graph data, or provider documents.

## Mobile, theme, and accessibility

- The selector uses the Phase 2B `Dialog`, `DialogBody`, `DialogFooter`, `FormField`, and `Input` contracts.
- It has no raw colors, fixed desktop widths, stock imagery, or nested result scroller. The dialog owns vertical scrolling.
- Existing static layout coverage passes at 320, 360, 390, 430, 768, 1024, and 1440 px.
- All five themes and both density modes remain covered by the design-system validation.
- Creature/Quest names are text, so icons and images are never the sole accessible label.

## Map→Hunt

The optional Map→Hunt shortcut was not added because the current Planner has no URL/state preselection contract tied to a verified guild workspace. A future minimal contract should be `/guild/hunts?zone=<canonical-uuid>`, consumed only after resolving an authorized current guild context and validating the UUID with the same backend rule. Phase 3F does not depend on it.

## SpawnLocation and legacy protection

SpawnLocation was not modified. The Planner reads the canonical Hunting Zone projection, which may merge retained SpawnLocation evidence under the existing policy, but never reads or writes SpawnLocation directly. The 2,654 bridge-only SpawnLocation links remain available. The 973 legacy free-text HuntZones cannot enter picker results or the canonical persistence field.

## Remaining Planner gaps and future recommendation contract

- Media remains mostly `reference_only`; a policy-compliant cache is still needed before those images can appear.
- Most canonical zones remain knowledge-only on the map.
- The bounded calendar summary intentionally exposes only the first resolved access Quest; full detail owns the complete list.
- Map→Hunt preselection needs an authenticated guild-context route contract.
- No recommendation/scoring was implemented. A later scorer can use the stored canonical UUID to join current player level/vocation, zone level/vocation metadata, authoritative Creatures, access Quests, and historical Hunt/attendance outcomes. It must version its evidence, preserve unknowns, explain factors, avoid deriving level/vocation from Creature difficulty, and remain advisory rather than mutating schedules.

## Phase 3G NPC Directory handoff

Phase 3F found no NPC dependency in Guild Hunt persistence or lifecycle. Phase 3G should keep the same boundaries: canonical `KnowledgeEntity` UUID as identity; active/public provider-backed picker/directory records only; exact NPC↔Location and NPC↔Quest relationships with unresolved/ambiguous states preserved; trusted Phase 3D spatial navigation without coordinate reconstruction; local/cached media only; bounded list summaries with batched relationship projection; full detail on demand; and no promotion of free-text names into NPC identities. NPC discovery may later enrich a selected zone, but it should not be copied into `GuildHunt` rows.
