## 3. Canonical Hunting Zone identity

The authoritative identity is the `KnowledgeEntity.uuid` for `entity_type=hunt_zone`. `HuntZone.id` remains the domain/projection bridge needed by existing routes and foreign keys. No third identity was added.

Detail responses expose `canonical_identity = {canonical_id, domain_id, aliases, provider_mappings}`. Existing additive top-level `canonical_id` and `knowledge_entity_id` fields remain. A provider mapping is `(provider_id, entity_type=hunt_zone, external_id) -> canonical UUID`; aliases are exact normalized names unique within the entity type. Numeric lookup resolves `HuntZone.id`; slug/canonical-name/alias lookup is exact. Search may still perform ordinary text discovery, but it neither resolves nor creates entities.

## 4. HuntCatalog disposition

Development data contains zero `HuntCatalog` rows. It is a non-authoritative, free-text duplicate and its removed UI must not be restored.

| HuntCatalog field/action | Disposition |

| `name` | Already represented by canonical identity/HuntZone. |

## 5. List contract

`GET /hunt-zones/` and `/hunt-zones/highlights` return `HuntZoneList`: stable IDs, basic level/vocation/difficulty fields, representative media, the shared spatial presentation/state, bounded creature preview/count/boss count/raw EXP summary, and an access indicator/count. Full creatures, spawns, access objects, aliases/mappings, and unresolved collections are omitted. Projection queries are batched by the requested page rather than issued per zone.

## 6. Detail contract

`GET /hunt-zones/{identifier}` returns the list fields plus canonical identity, deduplicated canonical creature references, unresolved creatures, access quests with semantics/provenance, canonical and unresolved locations, completeness metadata, and legacy `creature_spawns` as a compatibility bridge. The detail is richer without changing stored relationships.

## 7. Spatial behavior

The projection calls the Phase 3A `zone_spatial_presentations` batch pipeline. Precedence remains an explicitly resolved current TibiaMaps marker, then conservative stored local point/bounds, otherwise `knowledge_only`. Point, bounds, floor/Z, source, marker label, map asset metadata, and unmapped reason pass through unchanged. Known global bounds copied into TibiaMaps recovery placeholders are now excluded as non-observations. No coordinate is reconstructed from a city or name.

Public states are `resolved_point`, `resolved_bounds`, `knowledge_only`, or `unresolved` when unresolved canonical location evidence exists without geometry.

## 8. Creature behavior

Trusted current `has_creature` and inverse `appears_in` facts are preferred. `SpawnLocation` supplies migration coverage and display details when the graph is absent. When both paths point to the same Creature canonical UUID, one public creature remains and its `sources` and `relationship_types` retain both paths. Legacy rows are not deleted. Untrusted/unresolved graph targets remain in `unresolved_creatures`.

## 9. Boss behavior

`Creature.is_boss` is an existing provider-backed classification and is usable. A graph-only entity typed `boss` is also a boss. No name heuristic is used. Current boss coverage is almost entirely legacy SpawnLocation coverage, so canonical relationship normalization remains a gap.

## 10. Access Quest semantics

Direct trusted `requires_hunt_quest` means `required_for_access`. A trusted zone `requires_access` relationship followed by a trusted quest `unlocks_access` means `unlocks_access`; it is not silently promoted to a direct requirement. `leads_to`, quest location/occurrence, and merely related quests are not access requirements. Exact legacy quest FK/imported access names remain a compatibility source and can bridge only to a unique canonical quest. Resolved quests expose UUID/domain ID; unresolved names remain unresolved with relationship state, confidence, and provider.

## 11. City/region/location semantics

`city` and `region` are human-readable metadata. `located_at` is a semantic canonical relationship. Geometry is a separate spatial observation. Any one can exist without the others; a city never supplies a synthetic marker.

## 12. NPC findings

The registry has useful NPC relationship types in other domains, but development data has no verified zone-to-NPC semantic coverage suitable for this projection. Sharing a city is not evidence. NPCs are therefore not exposed from Hunting Zone detail in Phase 3B. Phase 3C/3F needs an explicit relationship vocabulary, source mapping, and coverage audit.

## 13. Loot findings

Zone loot can technically traverse zone -> Creature -> drops -> Item. The main payload must not expand every drop. No established notable-loot scoring rule exists, so Phase 3B exposes no zone loot. A later bounded/lazy endpoint is appropriate after defining whether it returns a complete paginated set or a source-backed ranking.

## 14. EXP/profit semantics

`avg_exp_hour` and `avg_profit_hour` are nominal stored local averages, but current rows lack reliable units/context, vocation dependency, range, and freshness evidence. No new estimate is calculated. Stored zero is projected as unknown (`null`), not a valid rate. Development coverage is zero for both after honest normalization.

## 15. Level/vocation/difficulty semantics

`min_level`, `max_level`, and `recommended_level` are recommendation metadata; `recommended_level` is not an access minimum. Vocation booleans and `recommended_vocations` express recommendations, not eligibility. `difficulty` is a descriptive provider/curated label, not a computed score. The 973 recovered rows' `min_level=0` and all-false vocation flags are import defaults, so the projection returns unknown. Only source-supplied/location-backed values are promoted.

## 16. Media precedence

Precedence is: cached local media asset; canonical Knowledge media reference; provider image explicitly supplied as `image_reference`; non-placeholder curated HuntZone image; missing. A map preview stays in `spatial.world_map` and is not misrepresented as zone artwork. Placeholder generation remains an explicit media-route compatibility option and is never advertised as representative media.

## 17. Missing-data contract

Public state fields distinguish canonical versus legacy identity, spatial state, creature state, representative-media state, access known/unknown, `supplied_fields`, and `missing_fields`. Null means no supported public fact. Significant gaps map to source missing, normalization missing, unresolved relationship, legacy-only, or semantic ambiguity; consumers no longer need to interpret zero/false recovery defaults as facts.

## 18. Canonical/legacy deduplication

Deduplication occurs only in the public projection and uses Creature canonical UUID first, legacy Creature ID only when no UUID exists. Canonical graph, inverse graph, and SpawnLocation provenance are merged. No KnowledgeRelationship or SpawnLocation row is mutated or deleted.

## 19. Unresolved preservation

Unresolved Creature, Quest, and Location graph rows remain unchanged in storage and are surfaced on detail with original name, relationship type, resolution state, confidence, and provider. The projection never creates a target to improve completeness. Knowledge Review remains the resolution path.

## 22. Bugs fixed

- Canonical creature relationships were ignored by HuntZone APIs.
- Canonical and legacy occurrences could duplicate one creature.
- Boss counts were not a stable zone summary.
- Canonical access Quest identity/semantics and unresolved names were omitted.
- List routes returned full SpawnLocation/Creature graphs.
- Canonical aliases/provider mappings were not exposed on detail.
- Stored zero rates and recovery-default level/vocation/access values looked factual.
- Recovery-placeholder global bounds/images looked zone-specific.
- List-card raw Creature EXP depended on a full spawn graph.
- Recommendation payloads had an independent zero/default interpretation.

Each repair is exercised in `test_hunt_zone_projection.py` or the retained regression suites.

## 23. Reproducible data repairs

No database row was rewritten. Repairs are deterministic, idempotent read-time projection rules backed by tests, so raw provider/recovery evidence remains replayable. No one-off SQL, fuzzy match, fabricated entity, coordinate, or relationship was used.

## 24. API compatibility

Changes are additive except that list/highlight responses intentionally omit the previously over-expanded relationship graph. Existing scalar fields remain. Detail retains `creature_spawns` and legacy quest fields while adding canonical structures. The current detail UI therefore continues to work. Both recommendation APIs retain their shapes; public recommendation normalization now shares honest field semantics, while full planner migration is deferred.

## 26. Frontend consumer findings

- `HuntZoneCard` independently formats vocation booleans, levels, rate truthiness, media, access, and raw EXP. It now receives a bounded summary but is not redesigned.
- Hunting Zone detail still renders `creature_spawns` and performs a legacy access fallback. The API compatibility bridge preserves it; later migration should render canonical `creatures` and unresolved states.
- Public Hunt Recommendations define a separate response interface and adapt it back into `HuntZone` for cards. Backend normalization is now shared; presentation consolidation remains Phase 3E.
- `TibiaMapPage` and map search use map-specific context/search APIs and the shared Phase 3A spatial evidence, not city-center guesses.
- Creature detail links through legacy spawn locations; it does not yet use the canonical zone projection.
- Quest detail has no first-class Hunting Zone relationship presentation and must not infer one from quest location text.

Future rule remains one canonical backend projection with multiple presentations.

## 31. Phase 3C requirements

- Normalize provider HuntZone records into canonical identities at materially higher coverage using exact IDs/names/aliases only.
- Resolve/review marker and Creature/Quest/Location relationships without fuzzy promotion.
- Define and ingest source-backed city/region/location semantics.
- Establish explicit verified zone-to-NPC relationship vocabulary before exposing NPCs.
- Add provenance/units/context/freshness contracts before importing EXP/profit recommendations.
- Decide whether canonical hunt zones are areas, locations, or both in provider normalization without generating duplicate identities.

## 32. Phase 3D Map requirements

- Consume canonical HuntZone identity/state consistently in map discovery and detail context.
- Improve exact marker-to-zone normalization coverage while retaining ambiguous/unresolved review queues.
- Keep authoritative marker > trusted local fallback > knowledge-only precedence and preserve floor/Z.
- Present bounds as bounds and points as points; never manufacture a centroid from city metadata.
- Reuse canonical zone media separately from map-floor imagery.

## 33. Phase 3E Hunt Planner requirements

- Make scheduled `GuildHunt` reference canonical Hunting Zone UUID/domain ID while retaining event-specific free text for exceptional targets.
- Replace independent recommendation/card reinterpretation with the canonical list/detail projection or a deliberately versioned planner projection built from the same service.
- Define source-backed rate units, vocation context, party context, ranges, and freshness before ranking on EXP/profit.
- Use access semantics (`required_for_access` versus `unlocks_access`) in planner warnings.
- Use the bounded creature summary for discovery and lazy detail for full creatures/loot.
- Migrate away from remaining HuntCatalog contracts, then deprecate the empty duplicate backend safely.
