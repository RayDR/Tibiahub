# TibiaHub V1.3 Phase 3H — NPC Provider Coverage and Relational Normalization

## Scope and preservation

Phase 3H changes data acquisition and canonical normalization behind the Phase 3G NPC Directory. It does not redesign public NPC UX and does not create direct NPC↔HuntingZone edges. The pre-existing index checksum is `5e69985215ef3589bb76b6193fd81aac63d2638aef86bdde8c16a1d343ecb2da`; no Phase 3H file was staged or committed.

## Root cause of the 46-NPC baseline

The live `Category:NPCs` catalog exposes 1,251 pages across 26 bounded pages at a batch size of 50. The baseline was not provider completeness:

- catalog continuation jobs used priority 90 while detail jobs used 100;
- the single worker therefore kept consuming repeated first-page/detail work while continuation jobs starved;
- two old continuations were eventually cancelled after remaining pending;
- four repeated roots and 201 historical detail attempts represented only 51 distinct detail documents;
- 46 of those documents normalized; five category/navigation pages remained raw-only;
- six exact non-entity category pages were not filtered before detail scheduling.

Phase 3H gives NPC continuation jobs priority 190, keeps roots at 200, batches up to 50 detail page IDs per provider request, filters only the six verified non-entity titles, and preserves malformed stable-ID pages as `npc_raw:*` documents rather than creating entities.

## Canonical algorithms

Identity resolution remains exact and entity-type constrained:

1. existing provider mapping;
2. exact provider external identity;
3. exact normalized canonical name or verified alias when unique;
4. ambiguous or unresolved.

No fuzzy, substring, Levenshtein, LLM, city-center or inferred-geometry fallback exists. Replays retain the same Knowledge UUID, aliases, provider mapping and current graph identity.

NPC locations keep prose separately from structured names. `predictloc` is classified as `moving`; multiple explicit provider position/city slots without a schedule are `multiple`; neither asserts a current singular location. Static structured names may create exact `located_at` facts. Prose alone cannot create Location or geometry.

Item `buyfrom` means the NPC sells the Item to the player and stores Item→NPC `sold_by_npc` (inverse `sells_item`). Item `sellto` means the NPC buys the Item from the player and stores `bought_by_npc` (inverse `buys_item`). One canonical relationship represents each Item/NPC/direction/provider fact. Multiple explicit offers remain in provenance context as `offers[]`; an arbitrary representative price is not selected. Semicolon qualifiers such as vial contents are retained, while the provider-only `sayname` display directive is discarded.

Pure integer prices without a currency token use the provider field's gold-coin contract. Explicit special currencies are preserved as normalized provider keys without conversion. A decimal price with no unit remains price-known/currency-unknown. Missing price is `null`, never zero.

Only structured `TransportCell` evidence creates `travels_to` (inverse `served_by_npc`). Destination identity is exact-only and price/currency remain in relationship provenance.

## Production integration and historical repair

- `npc_catalog` owns discovery, continuation and bounded detail batches.
- `npc_detail_batch` creates immutable per-page KnowledgeDocuments and invokes normal Knowledge normalization.
- normal Item detail ingestion creates/reconciles trade graph facts.
- normal NPC/Location normalization creates location/travel facts and re-resolves stale exact references.
- normal Knowledge normalization re-runs exact TibiaMaps marker reconciliation for the affected name/aliases.
- normal image sync includes NPC provider references in the shared validated local media cache.
- `normalize_npc_trade_relationships.py` is a bounded, cursor-based historical replay of immutable Item documents through the same normalizer; it is not the ongoing ingestion path.

The applied repair command was:

```text
python normalize_npc_trade_relationships.py --batch-size 250
```

It completed in 11 resumable batches. A subsequent representative replay of 100 items produced an identical relationship-context digest, `396c6c7e0c6b5d445c30a4a2577bb6e7`.

## Performance and review workflow

Warm 24-card directory projection with populated trade data uses 18 bounded queries and took 22.8 ms in the development measurement; query count remains constant as card count grows. A worst representative NPC detail (`Yasir`, 800 trade facts) uses 15 queries and took 332.7 ms after eliminating relationship N+1 behavior (previous diagnostic: 1,614 queries / 1,143.7 ms).

Unresolved and ambiguous `located_at`, `travels_to`, `sold_by_npc` and `bought_by_npc` facts use the existing Knowledge Review records. The only UI compatibility change is English/Spanish labels for the six new forward/inverse relationship names. No NPC-specific review system was added.

There are zero current direct NPC↔HuntingZone graph edges.

## Remaining gaps and conclusion

- 1,029 NPCs have only unresolved structured place identity; 146 have both an exact broader place and unresolved subarea.
- 1,235 NPCs have no exact TibiaMaps marker.
- 139 structured travel destinations lack an exact canonical Location.
- 12 trade facts lack a safe singular NPC identity.
- current provider documents expose no structured Quest relation.
- 1,235 NPC media references remain reference-only until normal media sync caches them.

NPC data is mature enough to close Phase 3: discovery is complete for the configured authoritative provider, identity/replay is stable, graph semantics are explicit, public queries are bounded, and every remaining gap is represented honestly. The recommended next V1.3 phase is release hardening and operational Knowledge Review/coverage monitoring, not another public NPC UX redesign.
