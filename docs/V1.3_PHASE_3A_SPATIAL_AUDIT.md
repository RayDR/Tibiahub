## 5. Coordinate-system contract

- Canonical game geometry uses Tibia absolute tile coordinates: X grows east/right, Y grows south/down, and Z is Tibia's native floor ID from 0 through 15. Ground is Z=7. The display label is `7 - z`: Z=6 displays `+1`, Z=7 displays `0`, and Z=8 displays `-1`.
- Point coordinates are all-or-none XYZ. No general default Z is safe. A TibiaMaps marker safely supplies Z because its `z` selects the source floor.
- Spatial PostGIS geometry uses SRID 0 because this is a game grid, not a geographic CRS. Points are PointZ; regions are MultiPolygonZ; complete routes can be LineStringZ.
- Current floor DB extents are `min_x=31744`, `min_y=30976`, `max_x=34304`, `max_y=33024`, with the upper bounds exclusive in backend placement checks. Every image is 2560×2048, so one game tile maps to one source pixel.
- `TibiaMapViewer` world mode uses `pixel_x=(x-min_x)/(max_x-min_x)*width` and `pixel_y=(y-min_y)/(max_y-min_y)*height`, then Leaflet `CRS.Simple` receives `[pixel_y,pixel_x]`. `LocalizedMapPreview` applies the same offsets as CSS percentages. No Y inversion is used for authoritative world mode because both Tibia Y and image Y grow downward. Only the explicit legacy-image mode flips Y.
- Provider `bounds.json` contains `xMax=34048` and `yMax=32768`, while width/height imply the larger image extents stored in DB. Import and rendering consistently use `xMin/yMin + width/height`; the raw maxima are retained as provenance and must not be mixed into pixel scaling without first understanding their upstream meaning.
- HuntZone `map_bounds` is not automatically compatible with the normalized `{min_x,min_y,max_x,max_y}` contract. The live values use raw `xMin`/`xMax` keys and are global dataset metadata, which correctly prevents them from being mistaken for a zone centroid.
- No current frontend path was found treating image pixels as absolute tiles in world mode. Asset coordinates and entity coordinates are separate and joined only through the floor bounds transform.

## 8. Default-map bootstrap behavior

`/map/bootstrap` loads one selected floor (default native Z=7), all 16 available floor IDs, base-map/pathfinding URLs and bounds, and a small hard-coded list of town markers. It does not load Creature, Quest, NPC, item, or HuntZone datasets. `TibiaMapPage` initializes all layer toggles as enabled, but makes a layer request only after a search query of at least two characters. Results switch to their evidence floor; null-Z evidence would be shown across floors, though trusted points require Z.

The live bootstrap returns zero towns. This is not a hidden-marker, CSS, floor, or request-shape bug: there are no canonical `town` entities. Edron is typed `location`, and bootstrap explicitly requires a resolved marker whose canonical entity type is `town`. Later work should normalize/classify towns rather than weaken exact identity checks. Responsible future bootstrap remains base map + a small verified town set; large entity layers should use search, layer/viewport queries, lazy loading, and clustering as needed.

## 9. Floor/Z findings

- All 6,396 source markers have valid native floors and in-bounds XYZ after import filtering.
- Point DTOs and route steps already reject partial XYZ; no floor is inferred from X/Y.
- Region GeoJSON requires 3D integer positions, but persistence previously left `min_z/max_z` null when callers omitted redundant explicit fields. Phase 3A derives all XYZ bounds from the validated geometry and regression-tests the behavior.
- Search focus and detail previews preserve marker Z. Frontend display conversion is consistently `7-z`.
- HuntZone direct fields have no live partial-XYZ cases because there are no live XYZ cases at all. Global raw bounds have Z range 0–15 but cannot supply a zone floor.
- Region focus currently uses `min_z` if a region spans floors; the future presentation contract should explicitly describe multi-floor areas instead of implying a single floor.

## 13. Quest spatial findings

Quest location concepts include start NPCs, overall and mission locations, access records, access destinations, and potentially unlocked Hunting Zones. They are not interchangeable. Current search traverses `starts_at_npc`, `occurs_at_location`, and `mission_occurs_at_location`; it does not flatten `unlocks_access → leads_to` into a quest point. That is correct: an access destination is distinct evidence and should later be labeled as such.

Among 125 non-group bridge quests, 124 have canonical UUIDs, two currently map through Edron, none has a direct marker, none has a current `starts_at_npc` relationship, and one has `unlocks_access`. `QuestMapInsets` is a presentation projection over entity spatial references, not an authoritative source. It should later group start, mission, occurrence, and access-destination evidence instead of collapsing them.

## 20. HuntCatalog retained-contract analysis

The Phase 2E premise does not match the surviving implementation. `frontend/src/services/huntCatalog.ts` and backend `/hunts` operate on a separate `HuntCatalog` table, not `HuntZone`. Its fields are free-text name, location, level range, vocation, EXP/profit rates, creatures, strategy, and notes. Reads require an active user; create/update/delete require a global admin. The live table is empty.

Actual HuntZone CRUD lives separately under Admin and operates on `HuntZone`. That broad full-row contract can touch canonical/provenance/spatial-adjacent fields and should not become the future canonical editor unchanged. Phase 3B should retain legitimate curated HuntZone fields (display metadata, recommendations, ratings, access and reviewed spatial evidence), add field protection/provenance and bounded authorization, then deprecate `/hunts` after confirming no external consumer and preserving any non-empty deployment data. The obsolete HuntCatalog UI must not be restored.

Guild Hunt Planner is separate again: `GuildHunt` stores free-text `location` and `target`, and the live table is empty. Those fields remain valid for custom/historical hunts.

## 25. Proposed canonical spatial presentation contract

Do not replace current schemas in Phase 3A. The smallest useful later read model is:

```ts
type SpatialState = 'resolved_point' | 'resolved_area' | 'knowledge_only' | 'unresolved';

interface EntitySpatialPresentation {
  entity_id: string;        // canonical UUID
  entity_type: string;
  label: string;
  spatial_state: SpatialState;
  focus?: { x: number; y: number; z: number; bounds?: Bounds };
  evidence: Array<{
    kind: 'point' | 'area';
    x?: number; y?: number; z?: number; bounds?: Bounds;
    label: string;
    source_provider: string;
    source_reference?: string;
    confidence: string;
    verification_state: string;
    geometry_source: string;
    relationship_path: string[];
    canonical_target_id?: string;
    legacy: boolean;
  }>;
  unresolved_locations: Array<{ name: string; relationship: string }>;
}
```

`resolved_point` requires complete trusted XYZ. `resolved_area` requires trusted bounds and explicit floor range. `knowledge_only` means canonical/conceptual location exists but no trusted geometry. `unresolved` means a retained location name cannot safely bind to one canonical target. The API may choose a focus but must preserve all evidence and provenance. Domain-specific labels must distinguish direct position, spawn, quest occurrence, quest start, mission, and access destination.
