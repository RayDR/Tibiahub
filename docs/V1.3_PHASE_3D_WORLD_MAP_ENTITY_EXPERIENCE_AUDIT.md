## 3. Map architecture before/after

Before, the base map already had all-floor local Leaflet imagery, pan/zoom, floor controls, partial/fuzzy text discovery, single-result focus, Hunt context, recent searches, URL query state, and a two-state `mapped`/`knowledge_only` response. Search was also acting as the only entity retrieval path. All visual-category buttons behaved as a mutually exclusive search filter, the “known towns” bootstrap returned zero development markers, legacy HuntZones appeared in search, partial failures collapsed into empty results, and areas were centered rather than fitted.

After, search remains universal discovery while visual layers load independently and lazily. Every canonical result has the same identity/spatial/navigation contract. A small authoritative Location set gives the default map useful context. Point, area, knowledge-only, and unresolved states differ explicitly. Layer failures are isolated from the base map and other layers. Markers can select their canonical preview. Area focus uses guarded fit-bounds. Legacy HuntZone text cannot become a result or marker.

## 4. Canonical result contract

The existing Phase 3A result shape was extended additively. A result now carries:

- stable result ID derived from canonical UUID;
- `canonical_entity_id` plus compatibility domain `entity_id`;
- entity type, display name, slug, representative media, subtitle;
- `spatial_state`, compatibility `geometry_status`, point, bounds, floor, source;
- zero or more spatial evidence records with semantic role, relationship chain, state, source provider, and confidence;
- location labels, compact domain preview facts;
- `navigation_url` plus compatibility `to`.

Backend builders and the shared TypeScript interface use this contract for Location, NPC, Creature, Boss, Quest, Hunting Zone, Item search, and compatibility Town results.

## 5. Search behavior by entity type

Search remains bounded, local, and partial-text based for discovery; selection is tied to returned canonical UUID, never the text match.

- **Location:** canonical bridge name/region; point or knowledge state; canonical detail route.
- **NPC:** canonical name/location/occupation; mapped only through trusted direct/relationship evidence. Text location remains subtitle, not geometry.
- **Creature:** canonical, visible Creatures; one-to-many spatial evidence retained. Bosses use stored `is_boss` classification.
- **Quest:** canonical non-group Quests; name/location discovery; multiple role-preserving evidence targets.
- **Hunting Zone:** only the single canonical HuntZone is searchable. The 973 legacy rows are excluded.
- **Item:** canonical discovery remains supported. Geometry exists only through a resolved `dropped_by`/`drops` → Creature → trusted spatial path and is labelled `obtained_from`; direct Item marker matches are not treated as Item location.

Search performs no writes and creates no Knowledge resolution.

## 6. Spatial-state behavior

- `resolved_point`: render marker, select floor, center while preserving useful zoom.
- `resolved_area`: render semantic bounds, select floor, fit bounds with padding and maximum zoom 3.
- `knowledge_only`: keep the canonical result and detail action visible; no marker.
- `unresolved`: keep the result and known text visible, explicitly explain unresolved spatial evidence; no marker.

The compatibility `geometry_status` remains `mapped` or `knowledge_only` for existing consumers. Explicit unresolved state is derived only from current unresolved/ambiguous spatial links or spatial relationship evidence.

## 7. Default bootstrap

The old Town bootstrap currently resolves zero development records because no canonical `town` entities exist. Bootstrap now also returns up to 40 trusted canonical Location results. Development has two: Edron and Bulltaur Lair. On an unparameterized first visit, the UI focuses preferred known-town Edron and switches to its authoritative floor. Explicit URL floor/query state is never overridden. The old `towns` field remains for compatibility.

## 8. Layer architecture

Independent visual layers are Location, NPC, Creature, Boss, Quest, and Hunting Zone. Each has a bounded `GET /map/layers/{layer}` response capped at 250 resolved entities and an optional floor filter. The frontend requests a layer only when enabled, caches it for five minutes, and can enable any combination. Location bootstrap seeds the initial layer without a redundant request. Search is independent of enabled visual layers.

Retrieval decisions:

- Locations: tiny authoritative bootstrap plus lazy cached layer.
- NPCs: lazy; only one currently resolves.
- Creatures/Bosses: separate lazy calls; 109 resolved entities/171 targets remain comfortably below the cap.
- Quests: lazy and role preserving.
- Hunting Zones: lazy, currently empty.
- Items: discovery-only, never a global visual layer.

No all-creatures/all-spawns request occurs at startup and no tile/vector infrastructure was introduced.

## 9. Location layer

Only canonical Locations with trusted spatial evidence are returned. Development exposes Edron at z=9 and Bulltaur Lair at z=8, both as exact TibiaMaps points. The remaining 30 canonical Locations stay searchable but marker-free. Free-form Location prose is not consumed.

## 10. NPC layer

Of 46 canonical NPCs, A Swan resolves through `located_at → Edron`; 42 have unresolved spatial references and three are knowledge-only. Only A Swan enters the marker layer. Stored provider location text, occupation, Quest count, trade indicator, image, and canonical NPC route remain available in result/preview data. Text-only NPC locations are tested as visible without markers and are never placed at city centers.

## 11. Creature layer

There are 2,202 canonical Creature entities. The public map domain set contains 2,192 visible entries: 1,644 normal Creatures and 548 Bosses; ten hidden entries are excluded. Sixteen normal Creatures have 61 trusted points. Creature evidence remains an array, so Antenna and other multi-marker Creatures retain all occurrences. Legacy Spawn evidence can contribute only through a canonical HuntZone with trusted geometry; the 973 manufactured legacy zones are filtered out at this boundary.

## 12. Boss presentation

Boss status comes only from `Creature.is_boss`. Ninety-three Bosses have 110 trusted points. Bosses have a separate independent layer and a visually distinct thick-border `B` marker when no real sprite is used. No name heuristic exists.

## 13. Quest layer/multi-target semantics

There are 403 canonical Quest entities, of which 124 are non-group actionable Quest records used by map browsing. Two currently resolve to two trusted points; 118 are knowledge-only and four have unresolved spatial evidence. Evidence remains an array and retains roles such as `start`, `mission`, and `location`. Tests cover one Quest with two locations on different floors and distinct `location`/`mission` roles. Group/catalog pages are not rendered as individual Quests.

## 14. Hunting Zone layer

The layer contains zero markers. Iksupan is the one canonical HuntZone and remains searchable in `unresolved` state because it has structured but unresolved location evidence and no trusted geometry. All 973 legacy HuntZones are excluded from canonical search and layer queries. Neither free-text `Creature.locations` nor the historical global map placeholders are rendered.

## 15. Item relationship behavior

Items are search-only. Direct Item marker identity is not presented as “the Item is here.” A map target is emitted only when a current, high/verified `dropped_by`/`drops` relationship reaches a Creature with trusted spatial evidence. Result evidence uses role `obtained_from` and retains the relationship chain. Development contains 720 Items with potential semantic coverage through 1,995 Item/Creature pairs over 109 mapped Creatures. A sampled Enchanted Theurgic Amulet search resolved in 74.1 ms with `obtained_from: dropped_by → mapped_creature`.

## 16. Marker visual system

Real local Creature sprites remain preferred. Otherwise markers display a type letter and type-specific border shape/style for Location, NPC, Creature, Boss, Quest, Hunting Zone, Item selection, and exact-position groups. Meaning therefore does not depend on color. Styles use TibiaHub semantic theme tokens only; no raw color was added. Selected entity information is duplicated in accessible DOM preview content.

## 17. Overlap handling

The 286 raw resolved TibiaMaps markers occupy 286 unique XYZ positions, so a clustering dependency is unjustified. Derived evidence does create exact overlap: Edron can simultaneously represent the Location, A Swan, and two Quests. Enabled layer markers at identical XYZ are therefore grouped deterministically into one `+` marker with count and sample names. Non-identical nearby points are left untouched.

## 18. Floor behavior

All 16 verified floors remain unchanged. Selecting any point/area automatically chooses its z floor. Lazy layer evidence is filtered to the active floor in the UI; the API also supports server floor filtering. Manual floor changes update markers. If a selected entity's focus lies on another floor, the preview remains visible and provides an explicit return-to-floor action. Tibia z values and display-floor formatting remain unchanged.

## 19. Bounds/region behavior

Trusted bounds render as a semantic rectangle and use fit-bounds with 48px padding and maximum zoom 3. Point-only evidence never renders a region. Development currently has zero trusted area records, but backend and frontend focused tests cover a canonical bounded HuntZone and verify `resolved_area`. Historical placeholder bounds remain rejected by the Phase 3A presentation contract.

## 20. Search→focus

Selection chooses the requested evidence label when supplied, otherwise the first trusted target. It changes floor, centers a point or fits an area, highlights/selects the canonical result, opens the preview, stores a bounded recent target, and writes canonical entity/type/slug/floor state to the URL. A partial text match is never reused as identity.

## 21. Entity preview

The compact preview includes real media when available, name, entity type, spatial status, coordinates/floor or honest missing-state text, source location subtitle, multiple-target selectors, and up to four domain facts. Facts include Creature classification/difficulty, Boss flag, NPC occupation/trade/Quest count, Quest location/level/start NPCs, Location kind/region/parent, and Hunt city/region/Creature/access context. Hunt Creatures retain their existing sprite strip. This remains a preview, not a detail-page replacement.

## 22. Map→detail

Each canonical search/layer result carries its canonical detail route. Preview actions use that route, normally a canonical slug rather than display-name reconstruction. Compatibility Town results omit detail navigation when no domain route exists.

## 23. Detail→map

One shared `buildMapEntityUrl` helper now builds links with canonical UUID, type, name, slug, floor, and optional evidence label. Quest insets and mapped Hunt detail use it. Existing Creature, NPC, and Location `MapMetadataPanel` instances receive a small target descriptor and expose the same map link only when trusted geometry exists. Detail pages were not otherwise redesigned.

## 24. Loading/error/degraded states

Base-map asset loading/failure, search loading, no matches, search API failure, per-layer loading, per-layer failure, knowledge-only selection, and unresolved selection have distinct feedback. A search or layer failure does not clear the floor asset or successfully loaded layers. Layer cache supplies five-minute local reuse; no unlabelled stale-data claim is made.

## 25. Responsive behavior

At 320–768px the sidebar remains a bottom overlay capped at 52% height, horizontally scrollable layer controls stay reachable, and map visibility remains primary.
